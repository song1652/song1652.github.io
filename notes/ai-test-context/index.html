AI 테스트 설계는
충분한 맥락에서 시작됩니다

Figma만으로 AI에 테스트 케이스 작성을 요청했을 때, 생성된 초안은 제가 검토하기에 필요한 내용의 약 70% 수준으로 느껴졌습니다. 이 경험을 통해 TC 작성의 출발점은 요청 문장뿐 아니라, AI가 제품을 이해할 수 있도록 제공하는 맥락이라는 원칙을 세웠습니다.

FigmaPRD·관련 문서TC 초안 검토
CONTEXT

화면을 전달하는 것만으로는 충분하지 않았습니다

처음에는 Figma를 제공하면 화면 구성과 사용자 흐름을 바탕으로 필요한 TC를 작성할 수 있을 것이라 생각했습니다. 하지만 생성된 초안을 검토하면서, 제가 기대한 검증 내용을 충분히 담기에는 정보가 부족하다는 점을 느꼈습니다.

화면은 제품이 어떻게 보이는지를 설명하지만, 어떤 조건에서 어떻게 동작해야 하는지까지 모두 설명하지는 않습니다. 기대 결과를 판단할 수 있으려면 화면 뒤의 기획 의도와 요구사항, 정책도 함께 이해해야 합니다.

INSIGHT

AI에 전달할 것은 화면과 검증의 근거입니다

이 경험을 바탕으로 PRD, 정책, 관련 문서 링크, Figma 등 제품을 이해하는 데 필요한 자료를 함께 제공하는 것을 TC 작성의 원칙으로 삼았습니다. 중요한 것은 자료의 양 자체보다, 기능의 목적과 화면 흐름, 판단 기준이 연결된 맥락을 전달하는 것입니다.

REQUIREMENTS

PRD와 요구사항

기능의 목적, 구현 범위와 기대 동작을 전달합니다.

POLICY

정책과 관련 문서

조건별 처리 기준과 예외 규칙을 함께 전달합니다.

UI & FLOW

Figma와 화면 흐름

요구사항이 실제 화면과 사용자 동작에 어떻게 연결되는지 보여줍니다.

ACCESS

자료를 읽었는지 확인

링크만 전달하는 데 그치지 않고, AI가 실제로 내용을 읽을 수 있는지 확인합니다.

WORKING PRINCIPLE

자료에서 확인한 내용과 추정을 구분합니다

함께 정리한 검토 기준은 명확합니다. TC의 사전 조건과 기대 결과가 제공한 자료에 근거해야 하고, 자료에 없는 조건이나 문서 간 충돌은 확인할 질문으로 남겨야 합니다. 부족한 정보를 그럴듯한 기대 결과로 채운 초안은 신뢰할 수 있는 검증 기준이 되기 어렵기 때문입니다.

TC 초안을 검토할 때 확인할 기준
  • 전달한 PRD·정책·Figma의 내용을 실제로 읽었는가?
  • 각 TC의 사전 조건과 기대 결과가 제공한 자료에 근거하는가?
  • 확인되지 않은 조건이나 문서 간 차이를 추정으로 처리하지 않았는가?
  • 실제 제품의 로직과 동작은 QA가 별도로 확인했는가?
QA PRINCIPLE

QA의 역할은 AI에 검증의 근거를 연결하는 것입니다

AI를 활용하는 QA에게는 생성된 TC를 검토하는 역할과 함께, 작성 전에 제품의 맥락을 구성하는 역할도 필요하다고 생각합니다. 어떤 자료를 제공하고 무엇을 확인해야 하는지 정리하는 과정이 TC 설계의 일부입니다. 초안의 완성도는 자료와 대조하고 실제 제품의 동작을 확인하면서 판단해야 합니다.

좋은 TC 초안은 충분한 제품 맥락에서 시작됩니다.
QA는 그 맥락을 연결하고, 검증 기준의 타당성을 확인합니다.
